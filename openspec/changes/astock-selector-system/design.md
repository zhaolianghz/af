## Context

本项目（`af`）是全新空仓库，目标是从零搭建一套 A 股选股系统。当前无任何代码、无既有规范可遵循，需在第一版同时确立技术栈、数据模型、模块边界、关键集成方式。

约束：
- 编排画布必须像 dify / n8n 一样可视化拖拽 + DAG 执行 + 实时调试。
- 必须支持多条选股方案并存且并行调度。
- 数据源以 A 股实时行情、K 线、财务、新闻为主，公开接口（东方财富/新浪/AKShare）做默认实现，预留私有网关接入点。
- 强依赖 A 股交易日历：调度时间必须落在交易日，避免周末/节假日空跑。
- 强依赖复盘：每条推荐要能跟踪到 T+1/T+3/T+5 收益与累计胜率。
- v1 范围不含实盘下单与跨市场。

利益相关方：
- **量化自营 / 个人投资者**：希望快速验证思路、可视化对比、跑历史回测。
- **策略研发**：需要把公式、阈值、节点配置化、可复盘。
- **运维**：需要稳定调度、执行可重试、日志可查。

## Goals / Non-Goals

**Goals:**

- 提供一个 dify/n8n 风格的可视化选股画布，零代码用户也能拖拽出"实时行情 → 技术指标 → 形态筛选 → 排序 → 落库"的完整 DAG。
- 多方案并存、独立调度、独立执行历史；方案可克隆、导入导出。
- 调度支持 Cron + A 股交易日历感知 + 手工"立即执行"。
- 推荐结果字段完备：`日期 / 股票名称 / 股票代码 / 加入区间 / 荐股方案编码 / 荐股方案名称 / 时段标签`。
- 时段标签 早盘 / 尾盘 / 无后盘 / 复盘 互斥，支持按标签统计。
- 绩效引擎：累计胜率、T+1 / T+3 / T+5 胜率、最大回撤、平均持有收益。
- 可视化大屏：持仓、今日推荐、方案胜率排行、胜率热力图、复盘入口。
- 数据源适配层可插拔，行情接口可替换。
- 单机一键启动（Docker Compose 一把起），亦可拆分布署。

**Non-Goals (v1):**

- 实盘交易接入 / 券商下单。
- 跨市场（港股 / 美股 / 期货 / 数字货币）适配。
- 因子库 / 因子挖掘 / 机器学习训练。
- 多账户券商同步（只做"模拟持仓"用于回放）。
- 移动端原生 App（v1 仅 Web，可后续加 PWA / Electron）。
- AI 自主"端到端"选股（v1 中 AI 仅作为**方案编辑助手**，不直接产出推荐或下单；推荐结果仍由编排 DAG 跑出）。

## Decisions

### 1. 技术栈：后端 Go + 前端 React/TypeScript

- **决策**：后端 Go（Gin + GORM + zap + viper），前端 React 18 + TypeScript + Vite + ReactFlow + ECharts。
- **理由**：
  - Go 部署单文件、无运行时依赖、并发模型适合"多方案并行 + 高频拉取行情"；自带的 goroutine + channel 适合编排引擎把每个节点并发执行。
  - ReactFlow 是社区里 dify/n8n 类编排最成熟的节点编辑器；ECharts 是国内大屏首选。
  - 单兵 / 小团队维护成本低、招聘容易、文档全。
- **备选**：
  - Python（FastAPI + Celery）→ 生态更丰富（pandas / TA-Lib / AKShare），但部署/调度/并发不如 Go 干净；CI/CD 镜像大。
  - Node.js（NestJS + BullMQ）→ 与前端同语言，生态尚可，但长跑任务稳定性弱于 Go。

### 2. 编排引擎：自研 DAG 执行器 + 节点插件化

- **决策**：自研轻量 DAG 执行器，节点以接口形式注册（`type Node interface { Run(ctx, in) (out, err) }`），JSON Schema 描述输入输出，节点间通过命名端口连接。
- **理由**：
  - n8n / dify 太重，自研可裁剪到只保留我们需要的特性：执行编排、可视化、调试日志。
  - 节点插件化让"实时行情 / K线 / 指标 / 筛选 / 排序"等都以独立包实现，热插拔。
- **备选**：
  - 直接 fork n8n → 学习成本高、二次开发受限、TS 全栈与我们后端 Go 分离困难。
  - 用 Temporal / Airflow → 强工作流但非"选股思维"，节点类型都要重写。

### 3. 数据源适配层：接口 + 多实现

- **决策**：`internal/datasource` 定义 `Quote / Kline / Fundamental / News` 四类接口；v1 必须实现至少 3 个源：`ds/eastmoney`（主源，实时五档 + 日线 + 财务）、`ds/sina`（备源 1，实时五档 + 日线）、`ds/akshare`（备源 2，日线 + 财务 + 龙虎榜）。统一走 `datasource.Manager` 路由，源顺序在配置文件中可调。
- **理由**：
  - 公开接口随时可能改 / 限流 / 挂掉，统一接口 + 适配器模式让切换不痛。
  - 至少 3 路：单源故障不能阻塞核心执行；3 路同时挂是极小概率事件，可以触发告警让人介入。
  - 用户原话："防止单渠道获取失败或者异常的情况"——多源是硬需求，不是 nice-to-have。

### 3.5 数据源可靠性"硬约束"：3 路 + 实时健康监控 + 单源熔断 + 全源告警

> 用户的核心痛点：行情单渠道失败 = 系统瞎。**这条不能静默**。

- **硬约束**：
  - **v1 必交付 ≥ 3 路数据源**（eastmoney + sina + akshare），任一可用即可继续执行。
  - **每源独立熔断**：单源 5 分钟内失败 > 5 次 → 熔断 10 分钟，期间不向该源发请求。
  - **每源独立心跳**：每 60s 写一次 `datasource_health` 表，含 `last_ok / last_fail / fail_count_5m / status (healthy / degraded / down)`。
  - **全源告警**：3 路全挂时立即走 7.5 多通道通知推"行情源全挂"告警（不依赖 cron 触发，下一次执行尝试时即刻发出）。
  - **切换可见**：每次源切换写 `provider_switch` 事件（from / to / reason / ts），前端"系统状态"页可见。
- **数据一致性校验**：
  - v1 增加 cross-source 校验：每天收盘后对比 3 路对同一只票的收盘价，偏差 > 0.5% 标 `data_inconsistency`，写入告警表。
  - 不阻塞执行，但需提示用户"该票数据源分歧"。
- **理由**：
  - 用户对"单点失败"高度敏感（hermes 经验），多源 + 实时监控是基本盘。
  - 公开源参差不齐：eastmoney 数据全但偶尔限流；sina 稳定但字段少；akshare 字段丰富但网络不稳。三源互补。
  - 数据源分歧不解决，未来胜率统计会被"源不一致"污染。

### 4. 调度：内嵌 cron + A 股交易日历感知

- **决策**：使用 `robfig/cron/v3` 做基础调度；额外实现 `TradingDayCalendar`（交易日历从 `tushare` / `akshare` 缓存到 DB），执行前判定"今天是否为交易日 + 是否在交易时段内"，非交易日 skip。
- **理由**：
  - 简单、无外部依赖。
  - 交易日历是 A 股系统的硬性需求，单独抽象避免每个方案都判断一次。

### 4.5 核心执行的"硬约束"：100% 确定性、零 LLM 状态依赖

> 用户反馈：hermes"经常记忆错乱"—— 根因是把 LLM 上下文当作执行状态机。本系统**必须**避免这个反模式。

- **硬约束**：
  - **核心执行路径**（cron → 交易日历判定 → DAG 执行 → 落库 → 通知）**禁止**任何 LLM 状态依赖。状态机跑在数据库（`run` / `run_log`）上，不跑在 LLM 上下文里。
  - LLM 仅出现在三类"非执行路径"：
    1. 节点的"AI 解释"输出（不影响执行结果，只生成给用户看的文本）。
    2. AI 助手改方案（用户确认后才落库，不参与自动执行）。
    3. 复盘报告的"AI 总结"段（生成辅助阅读文本，不影响数据）。
  - 即使 LLM 通道整体不可用，**核心执行链路必须继续跑**（AI 解释字段留空 / 标记 `ai_unavailable` 即可）。
- **执行状态机**：
  - 单次 run 的状态：`pending → running → (success | failed | partial)`，全部由 DB 字段驱动。
  - 失败可重试：retry 用同一个 `run_id` 写 `run_attempt` 表，保留所有历史 attempt。
  - 节点级日志：每节点一行 `run_log`，含 `started_at / finished_at / status / payload_in / payload_out / error`。
- **理由**：
  - LLM 上下文不可靠：上下文窗口有限、token 成本高、可能中途失忆、输出不确定。
  - 用户的核心诉求是"省心省力能赚钱"——核心链路必须**永远跑得动**，AI 是锦上添花不是主心骨。

### 5. 数据库：MySQL 8 主库 + Redis 缓存

- **决策**：MySQL 存方案、节点定义、执行历史、推荐结果、绩效快照；Redis 存实时行情、节点执行中间态、当日推荐热数据。
- **理由**：
  - 推荐结果量级（每天千条）× 多年累积仍远小于 MySQL 容量上限。
  - Redis 把实时行情去重 + 1 秒内复用，避免对公开接口高频拉取被限流。
- **备选**：PostgreSQL（功能更全但国内部署/运维成本略高）；ClickHouse（K 线历史量大时再考虑）。

### 6. 绩效引擎：每日收盘后批量回算

- **决策**：调度器在每个交易日 15:30（收盘 + 数据落定）触发 `PerformanceJob`，对所有"未到期"的推荐记录回算 T+1/T+3/T+5/累计收益与胜率，写入 `performance_snapshot` 表。
- **理由**：
  - 收盘后批量算一次，比"实时每条记录每分钟都算"省 90% 资源。
  - 历史绩效可回溯（schema 不可变）。

### 7. 推荐结果结构：方案编码 + 名称 + 节点快照 + 时段标签（多对多）

- **决策**：
  - `recommendation` 表字段：`id, run_id, date, stock_code, stock_name, entry_price_low, entry_price_high, strategy_code, strategy_name, node_snapshot_json, created_at`。
  - **时段标签改为多对多**：去掉 `recommendation.session_tag` 字段，新增 `recommendation_tag(recommendation_id, tag, tagged_at, source)` 关联表；`tag` 枚举 `MORNING / AFTERNOON / NO_POST / REVIEW`，`source` 区分 `AUTO_NODE`（由"时段"节点自动判定）/`MANUAL`（用户在执行配置里指定）/`AI_AGENT`（AI 对话式助手指定）。
  - 同一只股票在同一天被不同时段生成多条推荐时，标签**叠加**保留在历史中，方便复盘"这只票在早盘、尾盘、复盘都被推过"。
- **理由**：
  - 多对多更贴合"同一只票同一天可能在多个时段出现"的现实。
  - 记录 `source` 便于追溯标签来源，AI 自动打的与人工打的需要在审计上区分。

### 8. 时段标签语义（可叠加）

- **决策**：
  - `MORNING (早盘)`：9:30-11:30 期间生成的推荐。
  - `AFTERNOON (尾盘)`：14:00-15:00 期间生成的推荐（收盘前 1 小时，常用于"尾盘选股"）。
  - `NO_POST (无后盘)`：执行时段在交易时段内但策略明确不参与盘后决策（即"只在盘中用"）。
  - `REVIEW (复盘)`：15:00 之后生成的推荐，用于次日观察池。
- **理由**：四个标签覆盖 A 股四个典型决策时点，且同一只票可同时持有多个标签。

### 9. 可视化大屏

- **决策**：独立路由 `/dashboard`，1920×1080 适配大屏；ECharts 绘制胜率热力图 / 推荐分布 / 方案排行；首屏延迟 < 2s（首屏数据走 Redis 缓存）。
- **理由**：国内大屏是"门面"诉求，必须做；但要克制——v1 不做花哨动效，先把数据维度做对。

### 10. AI 对话式方案管理

- **决策**：
  - 前端在方案编辑器右侧挂一个常驻 AI 助手抽屉（可折叠），与画布共享上下文。
  - 后端新增 `/api/ai/chat` 接口，接收 `{strategy_id?, messages[], current_dag}`，调用 LLM（默认走 OpenAI 兼容协议，可替换为本地 Ollama/Qwen/DeepSeek），要求 LLM **输出结构化的"操作意图" JSON**，例如 `{action: "add_node", node: {type: "indicator", subtype: "MACD", params: {...}}}` / `{action: "update_param", node_id, param, value}` / `{action: "delete_node", node_id}` / `{action: "create_strategy", from: "scratch", name, code, dag}`。
  - 两阶段提交：LLM 返回"操作清单 + 画布 diff" → 前端在画布上**高亮预览变更**（节点闪烁 / 参数浮窗）→ 用户点"应用"才真正写入 `strategy.dag_json`。
  - 支持的操作：
    - **创建**："帮我写一个早盘 MACD 金叉 + 量比 > 2 的方案" → AI 生成完整 DAG + 节点参数。
    - **编辑**："把 MACD 的快线从 12 改到 10" → AI 找到对应节点、改 `fast_period`。
    - **复制 / 衍生**："基于方案 A 克隆一个 B，剔除北交所" → AI 复制 DAG + 应用 diff。
    - **删除 / 停用**："停用方案 X" → 状态机切换为 `disabled`（软删，保留历史）。
    - **导入**：粘贴一段文字 / 截图 OCR / 上传 JSON → AI 解析为 DAG。
- **理由**：
  - 降低非技术用户的使用门槛——说一句人话就能改方案。
  - 结构化输出 + 用户确认 + 落库的三步走避免 AI "幻觉改坏方案"。
  - LLM 走 OpenAI 兼容协议，本地/云端可切换，不锁死供应商。
- **备选**：
  - 直接让 LLM 改 `dag_json` 字符串 → 不可控、回滚难、用户难审查。
  - 用 n8n 风格的"自然语言节点"嵌入 → 工程量大、效果依赖 prompt 质量。

### 11. 单机一键启动：Docker Compose

- **决策**：根目录 `docker-compose.yml` 起 `app / web / mysql / redis`；开发时 `go run` + `npm run dev` 直连本地 MySQL/Redis。
- **理由**：低门槛；既支持 Demo 演示也支持生产部署。

## Risks / Trade-offs

- **公开行情接口限流 / 失效** → 多实现路由 + 失败降级到次级数据源（eastmoney → sina → akshare）；关键路径加重试 + 熔断。
- **编排画布复杂度高，节点种类多** → v1 节点限定 8-10 种（行情、K线、指标、形态、筛选、排序、去重、落库、通知），后续按需求扩展。
- **交易日历数据源同样依赖第三方** → 落库缓存到 `trading_calendar` 表，每周 cron 增量更新；断网时使用本地缓存。
- **T+1/T+3 复算在停服/补数据时缺数据** → 启动时检查 `performance_snapshot` 是否有断点，有则补跑当天所有方案的复算 job。
- **多用户协作时数据隔离** → v1 仅弱登录（账号 + 简单 JWT），策略/推荐按 `user_id` 过滤；v2 再加 RBAC。
- **前端画布性能（节点 > 200 时卡顿）** → ReactFlow 启用 `onlyRenderVisibleElements` + 节点 lazy load；后端按 `viewport` 返回节点元数据。
- **Go 与 Python 生态权衡**：放弃 Python 意味着放弃 pandas / TA-Lib 便利 → 用纯 Go 实现技术指标（库 `gonum` + 自研 `indicator` 包）覆盖 MA/EMA/MACD/KDJ/BBI/BOLL/成交量指标，量级足够 v1；后续如需更复杂指标，再以 sidecar 形式接 Python 微服务。
- **大屏图表依赖 CDN 资源** → 关键图表走 npm 自托管，避免公网 CDN 抖动。
- **回测功能未在 v1** → 用户要求是"跑 + 跟踪胜率"，并非"对历史数据回放"；回测放 v2，但数据模型为回测预留 (`run_type: LIVE | BACKTEST`)。
- **AI 对话改坏方案** → 强制两阶段：先 diff 预览，再用户确认；任何破坏性操作（删除节点、删除方案）需二次确认 + 撤销栈；LLM 输出走 JSON Schema 校验，校验失败 fallback 到对话继续问。
- **LLM 供应商锁定 / 私有数据外泄** → OpenAI 兼容协议 + `.env` 配置 base_url，可切 Ollama/Qwen/DeepSeek；方案定义（节点参数）允许走本地模型；行情与持仓等敏感字段不进 prompt 上下文。
- **多标签叠加导致数据膨胀** → `recommendation_tag` 仅存 (rec_id, tag, source) 三元组，相比 ENUM 字段每条推荐多 1-4 行；MySQL 索引 `(rec_id)` + `(tag, rec_id)` 即可，万级/日可承受。

## Migration Plan

新项目无既有数据/服务需要迁移。分阶段上线：

- **阶段 0（基础）**：DB schema + 后端骨架 + 登录 + 简单列表页。
- **阶段 1（编排 + 执行）**：ReactFlow 画布 + DAG 执行器 + 行情节点 + 落库。
- **阶段 2（调度 + 标签 + 方案）**：cron + 交易日历 + 时段标签 + 方案管理。
- **阶段 3（绩效 + 大屏）**：绩效引擎 + 胜率计算 + 可视化大屏。
- **阶段 4（打磨）**：权限、导入导出、复盘详情、通知（企业微信/钉钉）。

回滚策略：每阶段独立可运行；任何阶段发现重大问题，回滚到上一阶段 Docker 镜像版本即可。

## Open Questions

1. **行情接口选型**：默认走东方财富公开接口 + 备用新浪/腾讯？还是要付费 Tushare Pro / Wind 以保稳定？
2. **历史 K 线深度**：v1 是否需要 10 年 K 线？还是只取近 3 年够用？影响数据库容量。
3. **回测范围**：v1 是否要做"基于历史 K 线重放"功能？还是只做"实时跑 + 跟踪已发生的收益"？
4. **多用户**：v1 单用户本地使用即可，还是必须支持多账号协作？
5. **部署形态**：纯 Web（服务器 + 浏览器）？还是 Web + Electron 桌面（拷数据更方便）？
6. **通知渠道**：推荐出炉后是否需要推送到企业微信/钉钉/飞书？
